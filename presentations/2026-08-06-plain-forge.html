integration forge

what the product does about it

the product empowers your agent with the understanding of the rules of writing ***plain specs.

the user has the idea, the agent helps clarify it, writes the ***plain specs, and reviews them with the user.

you work with the agent exactly as you would when writing code. the procedures are there to clarify intent — and that intent is what gets baked into the specs.

02 · shape

two halves: a content library and a copy tool

the whole product is markdown files. the only code that runs is the installer that copies them into place.

forge/ — the product

forge/
  skills/<name>/SKILL.md   # 30 skills
              references/  # loaded on demand
              assets/      # 3 script generators only
  rules/*.md               # 14 rule files

a skill is frontmatter — name, and a description ending in a "use when…" trigger the host agent matches on — plus a prose body. operational bulk moves into references/ so it loads only when relevant.

why rules?

rules are autoloaded into the agent's context at startup, before any spec work begins. claude code reads rules/*.md natively, each file scoped to **/*.plain.

the alternative is relying on the model to decide, mid-task, that now would be a good moment to go and read the authoring guidance. that is exactly the unpredictability we want out of the loop.

agents without native rules wiring reach the same files through load-plain-reference, which loads only the ones the current task needs.

05 · the flagship workflow

forge-plain: an intent interview, then four gated phases

finish a phase — on disk and approved — before the next one opens. no drafting ahead.

PHASE 0

intent

five questions: problem, user, outcome, success criterion, boundary. nothing written to disk.

gate · user confirms brief
PHASE 1

gate · review agent
PHASE 4

gate · dry-run green

maintaining with plain-forge

add-feature

the same loop and the same gates, scoped to one feature on an existing project. its own short intent step; ends on plain-healthcheck.

debug-specs

something in the rendered app is wrong: it traces the failure back to the responsible spec and fixes the spec, never the code.

run-codeplain

supervises a live render, watches for stuck conformance loops and complexity errors, hands off to a spec-edit skill and resumes. experimental.

06 · inside a phase

the loop runs per topic. the gate runs once.

this is what phase 1, 2 and 3 from the previous slide actually do.

depth is allowed

one question per call, not per topic — a vague answer gets another pass at the same topic.

staleness is not

an answer that contradicts something already on disk is applied before the next question.

talk is not output

everything lands on disk — .plain files, test_scripts/, config.yaml.

07 · distribution

six agent layouts, and a manifest that makes updates safe

the install target is somebody else's directory, so the cli's whole design is about never touching what isn't ours.

agentprojectglobal
claude.claude/~/.claude/
codex · copilot · universal.agents/~/.agents/
forgecode.forge/~/forge/
opencode.opencode/~/.config/opencode/

the last two global paths are hardcoded exceptions. three agents share .agents/; the manifest records which label was chosen so update reports it correctly.

rules wiring, per agent

claude code
native — auto-loads rules/*.md, each scoped with paths: "**/*.plain"
opencode
a glob merged into opencode.json, absolute when global
forgecode
a fenced managed block in AGENTS.md
the rest
nothing generated — the router skill reads the directory on demand

manifest.json

every file written, plus the agent label and package version. nothing outside that list is ever a candidate for deletion, so a user's own and third-party skills in the same directory are structurally unreachable.

install
copies and records. refuses with exit 1 if a manifest or a legacy install is already there — it never overwrites in place.
update
finds every install across both scopes and all agents with no prompts, skips any whose recorded version didn't increase, re-copies, then prunes what no longer ships — each deletion confirmed individually, or all of them under --yes.
uninstall
deletes exactly the manifest's files, then the manifest, then the rules wiring, then any directory left empty.
a manifest-less install is detected by four signature skills and refreshed overwrite-only. uninstall on one refuses rather than guessing: it lists the directories to clean by hand and exits non-zero.
08 · challenges

challenges ahead

syncing with codeplain and ***plain — a maintenance problem
  • a new ***plain feature has to reach the rules before an agent can use it
  • a codeplain cli change — flags, config keys — has to reach the skills
  • rules that lag behind the language teach the wrong thing
evals — a research problem
  • how well specs written by plain-forge render
  • how often a first render passes conformance
  • comparing two revisions of a skill on the same input
observability — we don't own the agent
  • where is a rule failing
  • which skill is failing, and at which step
  • how often a phase gate is rejected before it passes
analytics — we don't own the agent
  • which skills users reach for most
  • how a given skill performs over time
  • testing out new skills before they ship

should we own the agent harness?

  • implementing our own agent
  • integrating plain-forge into codeplain

it gives observability and analytics a fighting chance, maybe also at evals

and how does any of that work when we ship open source?
